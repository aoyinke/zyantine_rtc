# 持续对话功能优化计划

## 问题分析

当前系统的对话流程是单次的：用户点击开始对话 → 录音 → 停止录音 → AI处理 → 播放回复 → 对话结束。用户需要每次重新点击按钮才能开始新的对话，体验不够流畅。

## 优化目标

1. 实现类似电话通话的持续交互模式
2. 点击一次"开始对话"按钮后，保持持续对话状态
3. 自动循环：用户说话 → STT → AI处理 → TTS → 播放 → 等待用户下一轮说话
4. 只有用户点击"挂断"按钮才结束会话
5. 全自动化流转，无需用户额外操作

## 实现方案

### 1. 前端修改

**核心思路**：修改对话状态管理，实现持续循环机制

**主要修改点**：

#### 修改 `ControlPanel.vue`
- 修改对话状态管理，将单次对话改为持续对话
- 调整UI状态显示，区分"开始/挂断"状态
- 修改 `toggleConversation` 函数，实现持续对话的启动和停止

#### 修改 `useAudio.js`
- 修改VAD处理逻辑，用户停止说话后不直接结束对话
- 实现"对话循环"机制：AI回复完成后自动重新开始监听
- 添加持续对话状态管理
- 修改 `handleUserStoppedSpeaking` 函数，移除结束对话的逻辑

#### 修改 `useWebSocket.js`
- 确保WebSocket连接在整个对话过程中保持
- 优化消息处理，支持持续对话流

#### 修改 `chat.js` (Pinia Store)
- 添加持续对话状态管理
- 优化状态流转，支持循环对话
- 添加对话结束事件处理

### 2. 后端修改

**核心思路**：确保后端能处理持续对话请求，保持WebSocket连接

**主要修改点**：

#### 修改 `ai_rtc_system.py`
- 确保系统能处理连续的音频流和对话请求
- 优化资源管理，避免每次对话都重新初始化组件
- 添加对话会话管理

## 实现流程

1. **用户点击"开始对话"**：
   - 连接WebSocket
   - 开始录音
   - 进入持续对话模式

2. **持续对话循环**：
   ```
   监听用户说话 → VAD检测到停止 → 发送音频到后端 → 
   后端处理：STT → AI → TTS → 返回音频 → 前端播放 → 
   播放完成 → 重新开始监听用户说话 → 循环...
   ```

3. **用户点击"挂断"**：
   - 停止录音
   - 断开WebSocket连接（可选）
   - 结束对话状态
   - 重置相关组件

## 关键技术点

1. **VAD（语音活动检测）优化**：
   - 确保准确检测用户开始和结束说话
   - 优化静音阈值和持续时间参数

2. **对话状态管理**：
   - 使用Pinia管理持续对话状态
   - 确保状态流转的正确性

3. **音频处理优化**：
   - 确保音频流的连续处理
   - 优化音频播放完成后的状态重置

4. **WebSocket连接管理**：
   - 保持WebSocket长连接
   - 处理网络波动和重连

## 预期效果

1. 用户体验提升：一次点击，持续对话
2. 更自然的交互方式：类似电话通话
3. 自动化流转：无需用户重复操作
4. 清晰的结束机制：点击挂断按钮结束对话

## 风险评估

1. **资源占用**：持续对话可能导致更高的资源占用
   - 缓解方案：优化资源管理，及时释放不必要的资源

2. **网络稳定性**：长时间WebSocket连接可能受网络波动影响
   - 缓解方案：添加重连机制，确保连接稳定性

3. **音频处理延迟**：持续处理可能导致延迟累积
   - 缓解方案：优化处理流程，确保实时性
