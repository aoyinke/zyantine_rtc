# 语音识别速度慢的原因分析

经过对代码base的分析，我发现语音识别速度慢主要有以下几个原因：

## 1. 非流式ASR调用
- 当前使用的是字节跳动的非流式ASR API (`enable_nonstream`: False)，需要等待完整音频处理完成后才能返回结果
- 每次调用STT都要重新建立WebSocket连接，包含认证和握手过程

## 2. 音频分段发送延迟
- `AsrWsClient.send_messages`方法中，每次发送音频段后都有固定的200ms延迟
- 这个延迟是为了模拟实时流式发送，但对于非流式API来说是不必要的

## 3. VAD检测延迟
- 前端VAD配置中，`maxSilenceDuration`设置为0.6秒，用户停止说话后需要等待0.6秒才能触发处理
- 后端完全依赖前端VAD检测，没有进行二次验证

## 4. 网络传输开销
- 前端使用base64编码发送音频数据，增加了33%的数据大小
- 音频数据没有进行任何压缩，直接传输原始PCM数据

## 5. 音频处理流程
- 后端需要将所有音频块合并成一个大数组，在音频较长时会占用较多内存和时间
- `convert_audio_format`函数每次都重新创建WAV头，存在优化空间

# 优化方案

## 1. 改为使用流式ASR API（优先级：高）
- 修改`stt.py`中`RequestBuilder.new_full_client_request`方法，将`enable_nonstream`设置为True
- 实现真正的流式处理，边发送音频边接收识别结果
- 优化`AsrWsClient.start_audio_stream`方法，实现双向流处理

## 2. 减少音频分段发送延迟（优先级：高）
- 修改`AsrWsClient.send_messages`方法，移除固定的200ms延迟
- 或者根据实际网络情况动态调整延迟时间

## 3. 优化VAD检测（优先级：中）
- 调整前端VAD配置，将`maxSilenceDuration`从0.6秒减少到0.3秒
- 在后端添加轻量级VAD处理，双重保障，减少不必要的音频传输

## 4. 优化网络传输（优先级：中）
- 考虑在前端使用二进制格式直接发送音频数据，避免base64编码开销
- 实现音频数据的批量发送，减少WebSocket消息数量

## 5. 优化音频处理流程（优先级：低）
- 优化`convert_audio_format`函数，避免重复创建WAV头
- 考虑在后端进行音频压缩，减少存储和传输开销
- 实现边接收音频边处理的机制，避免等待完整音频

# 预期效果

通过以上优化，预计可以将语音识别的整体延迟从当前的2-3秒降低到1秒以内，显著提升用户体验。特别是改为流式ASR API后，用户可以在说话过程中就看到初步的识别结果，大大减少等待时间。
